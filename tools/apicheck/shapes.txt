# The shapes we put on each route, held against the firmware's own declarations.
#
# routes.txt proves the routes still exist. This file is the other half: what
# travels over them. Every route in routes.txt needs at least one row here, and
# a route with nothing to diff needs a row saying so and why -- so an omission
# reads as a decision rather than as something nobody got to.
#
# Writing the row is half the value. Naming the upstream type forces whoever
# adds a client method to open that struct, which is the step #31 skipped.
#
# Columns (whitespace-separated; the last one runs to end of line):
#
#   <route>  <METHOD>  <dir>  <upstream>  <ours>
#
#   dir        req -- the body we send, which upstream binds and validates
#              rsp -- the envelope's `data`, which upstream encodes and we decode
#   upstream   <path in sipeed/NanoKVM>#<TypeName>, or `-` when upstream declares
#              no type for this direction
#   ours       <path in this repo>#<TypeName> to diff the two, or a marker:
#                passthrough: <why>  upstream has a type; we hand the decoded map
#                                    to the MCP client without reading fields
#                untyped:     <why>  no struct on either side (streams, binary,
#                                    query strings)
#                none:        <why>  the direction carries no payload
#
# A route may have several rows. Nested types get their own row rather than
# being walked implicitly, so a failure names the struct it is talking about.
#
# What this cannot see: framing and transport semantics. The /api/ws HID byte
# protocol and the fact that /api/stream/mjpeg never ends are not declared as
# types anywhere upstream, so no row here covers them. Those are guarded only by
# fakes that behave the way the firmware behaves.
